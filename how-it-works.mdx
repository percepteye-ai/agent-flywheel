## The flywheel loop

`fw.serve()` does two things: it describes your agent once, then claims work forever. Every connection starts from your process. The SDK dials out to Agent Flywheel, and nothing dials in to your process.

The loop separates agent execution from evaluation. Your agent runs in its own environment with a single-use credential, adapters record what happened from outside the agent's decision-making process, and the control plane scores the resulting trajectory against compiled checks.

## The six beats

| beat | what happens | who does the work |
| --- | --- | --- |
| ⓪ Onboard | The SDK describes your agent from inside its own process and registers it once. | Automatic. Set `introspect=False` to opt out. |
| ① Claim | Your process long-polls for a rollout and receives a lease. | Your process dials out. |
| ② Run | A fresh child process runs with its own environment and a single-use credential. | Your agent runs unchanged. |
| ③ Record | Tool calls become `ok`, `failed`, or `unknown`; artifacts are collected on every path. | Adapters observe from outside the agent. |
| ④ Score | Tasks come from your real tool surface and are graded against compiled checks. | PerceptEye evaluates the rollout. |
| ⑤ Improve | Your production agent picks up the promoted policy. | One call at startup applies the policy. |

These beats run in order for each lap, but not every network lane runs at the same frequency. Registration happens once, claiming repeats in a loop, and policy refresh happens at startup or at an explicit refresh point.

## Once, at startup

`serve()` performs its preflight checks in a fixed order. The order matters because mode resolution happens before credential validation and before the SDK opens any socket.

| order | check | result |
| ---: | --- | --- |
| 1 | Resolve the mode from the `mode=` argument, then `PERCEPTEYE_AGENT_MODE`, then `training`. | An unparseable value raises `ConfigurationError`. |
| 2 | Verify that transport is `attach`. | Any other transport raises `ModeNotAvailable`. |
| 3 | Resolve the control plane URL from `control_plane_url` or `PERCEPTEYE_CONTROL_PLANE_URL`. | A missing value raises `ConfigurationError`. |
| 4 | Resolve the API key from `api_key` or `PERCEPTEYE_API_KEY`. | A missing value raises `ConfigurationError`. |
| 5 | Create `artifacts_dir`. | A filesystem failure raises `OSError`. |
| 6 | Call `GET /health` and assert `flywheel/1`. | An incompatible or unavailable response raises `ConfigurationError`. |
| 7 | Scan for provider variables that cannot be routed. | The SDK emits `RuntimeWarning` and continues. |
| 8 | Resolve the entrypoint and verify that it supports the selected isolation mode. | Invalid entrypoints raise `EntrypointError` or `ConfigurationError`. |
| 9 | Describe the agent. | Description failures never prevent startup. |
| 10 | Register the agent with `POST /agents`. | Transport failures raise `TransportError`. |
| 11 | Send the rulebook with `POST /agents/{agent_id}/rulebook`. | Rulebook refusal is printed and does not stop startup. |
| 12 | Read `GET /policy/current`. | The policy is printed but not applied. A failed read becomes `{}`. |

Production mode does not need a control plane URL or API key for this startup path. After resolving production mode, `serve()` returns immediately rather than starting the training claim loop.

The startup policy read is informational. `serve()` does not apply the returned policy to your production agent. Apply policy explicitly with `apply_current_policy()` when your application starts.

## ⓪ Onboard: the agent describes itself

Onboarding runs inside the process that owns the agent. The SDK tries three probes in order and records the first matching framework representation.

| probe | matches | reads |
| --- | --- | --- |
| `google_adk` | `google.adk.agents.BaseAgent` | Instruction, tools, model, and sub-agents |
| `langgraph` | A compiled Pregel graph | Each user node as a sub-agent |
| `langchain` | An object with `tools` or `get_tools()` containing `BaseTool` objects | Tool name, description, JSON Schema, prompt, and model |

The SDK walks sub-agents to depth 4. It truncates the system prompt at 20,000 characters. A callable prompt is reported as `not-observed` because evaluating it could execute application logic or depend on runtime state.

The description distinguishes between not looking and looking but finding nothing:

- `tool_definitions: null` means the SDK could not inspect the tool surface.
- `tool_definitions: []` means the SDK inspected the agent and found no tools.
- The SDK never converts an unknown tool surface into an empty tool list.

The description is metadata, not execution authority. The SDK does not send tool source code, return values, credentials, rollout observations, or application data during onboarding.

### A CLI agent has no object to reflect on

A CLI agent does not expose an object for the SDK to inspect, so reflection returns `None`. The host describes the CLI through an `llm_input` event and writes the result to `discovered_agent.json`.

The SDK performs one warm-up at `serve()` time using a trivial prompt. The warm-up breaks the circular dependency in which the host needs to run the CLI to learn what the CLI is, while the CLI needs a description before it can run. The warm-up child is not a rollout and does not consume rollout capacity.

| bound | value | purpose |
| --- | ---: | --- |
| Warm-up wait | 90 seconds | Maximum time to wait for the CLI response |
| Grace period | 60 seconds | Time allowed for shutdown after the wait |
| Poll interval | 0.1 seconds | Interval used while checking warm-up state |

### An agent nothing can read: `describe=`

Use `describe=` when reflection cannot observe your agent or when you want to declare metadata explicitly.

```python
from percept_eye import serve

serve(
    entrypoint="support_agent:create_agent",
    describe={
        "system_prompt": "Route support requests using the available order tools.",
        "tools": [
            {
                "name": "lookup_order",
                "description": "Look up an order by its public order number",
                "input_schema": {
                    "type": "object",
                    "properties": {
                        "order_number": {
                            "type": "string"
                        }
                    },
                    "required": [
                        "order_number"
                    ]
                },
                "read_only": True
            }
        ],
        "model": "gpt-4.1-mini"
    }
)
```

The `describe=` value can declare:

- `system_prompt`, which supplies the system prompt when reflection cannot observe one.
- `tools`, using OpenAI-style or Anthropic-style definitions. Each tool can include a name, description, input schema, and `read_only` flag.
- `model`, which identifies the model used by the agent.
- Any field you declare explicitly, which takes precedence over reflected metadata.
- Any field you omit, which the SDK fills from reflection when reflection can provide it.

Set `read_only: true` for tools that do not mutate external state. This metadata helps classify the tool surface; it does not enforce read-only behavior at runtime.

An explicitly declared tool has `source_type: sdk_declared`. That value identifies the metadata source, not the execution identity. The entrypoint still determines what code runs.

`introspect=False` cannot be combined with `describe=`. The combination is contradictory because `describe=` provides metadata while `introspect=False` disables metadata discovery. The SDK raises an error instead of silently choosing one behavior.

### Opting out

Set `introspect=False` to disable automatic description. Only deliberate values disable onboarding. Omitting the argument, passing `None`, or leaving the setting unresolved does not opt out.

Opting out means the SDK does not probe the supported frameworks or populate discovered metadata through reflection. Registration still uses the remaining agent contract and explicit configuration.

## ① Claim: a long poll you open

Claiming is pull-only. Your process calls `POST /rollouts/claim`, waits for work, and receives at most the number of rollouts requested.

```http
POST /rollouts/claim
Content-Type: application/json

{
  "agent_id": "agent_support_triage",
  "max": 4,
  "wait_ms": 20000,
  "lease_ms": 600000
}
```

The request fields are clamped to the supported ranges before the control plane handles the claim.

| field | accepted range | meaning |
| --- | ---: | --- |
| `agent_id` | Registered agent identifier | Agent whose queue should be checked |
| `max` | 1 to 16 | Maximum number of rollouts returned by one claim |
| `wait_ms` | 0 to 25,000 | Maximum time to wait for available work |
| `lease_ms` | 1,000 to 1,800,000 | Duration for which the claimed work remains leased |

An empty queue returns HTTP 200 with an empty list and `poll_after_ms`. An empty result is not a failed request and should be treated as a normal polling outcome.

Claim requests are not replayable. The claim endpoint does not accept an `Idempotency-Key`, so retrying a timed-out claim can result in a separate claim attempt rather than a replay of the original request.

| event | meaning | handling |
| --- | --- | --- |
| `claim_empty` | The request succeeded, but the queue had no available rollout. | Wait for the returned `poll_after_ms` value before polling again. |
| `claim_failed` | The claim request failed before producing a usable result. | Record the failure and apply the client retry behavior. |

### Leases, heartbeats, and redelivery

A claimed rollout remains available to your worker only while its lease is valid. A daemon thread renews the lease at one-third of the granted lease duration.

The lease is a delivery guarantee, not the work budget. The rollout deadline can arrive before the lease expires, and the agent stops 10 seconds before that deadline. Configure the lease long enough for delivery and heartbeat traffic, but use the rollout deadline to bound the actual work.

If the control plane returns HTTP 410 for a heartbeat or lease operation, the SDK raises `LeaseLost` and kills the child process. The worker must not continue processing after lease ownership is lost.

A crashed worker does not send a cleanup call. The control plane reclaims the orphaned rollout when the lease expires, which can take up to 30 minutes when the maximum lease is in use.

`max_rollouts=N` is the only clean exit condition for a serving loop. A worker that stops for another reason can leave work waiting for lease expiry and redelivery.

## ② Run: isolate, then route

Each rollout runs with an isolation mode, an execution entrypoint, and a per-rollout provider route.

| isolation | timeout behavior | concurrency | entrypoint |
| --- | --- | ---: | --- |
| `subprocess` | Real timeout. The child process can be killed. | Any supported value | Must be importable |
| `inprocess` | Advisory timeout. Python cannot forcibly kill a running thread. | 1 only | Accepts an already-constructed object |

`subprocess` is the default because it gives the control plane a process boundary that can be terminated. Use `inprocess` only when the agent must receive a constructed object and the application can enforce its own cooperative cancellation.

### Environment crossing rules

The child receives a deliberately constructed environment. The SDK applies these rules in order:

1. It removes every inherited `PERCEPTEYE_` variable.
2. It sets `PERCEPTEYE_ROLLOUT_ID` and `PERCEPTEYE_TRAJECTORY_DIR`.
3. It sets the per-rollout provider endpoint variables last, including values such as `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `ANTHROPIC_BASE_URL`, and `ANTHROPIC_API_KEY`.

The last step ensures that the rollout-specific route wins over inherited provider configuration. Variables listed in `UNROUTABLE_PROVIDER_VARS` are removed rather than passed through, because they could send traffic outside the rollout gateway.

If your provider uses a custom variable name, configure `endpoint_env` with that name. The route still follows the same rule: the rollout-specific value is inserted after inherited environment variables have been filtered.

Two limits shape execution:

- `inprocess` supports concurrency of one because the constructed object and its thread share the host process.
- A Python thread cannot be killed reliably. An in-process timeout therefore remains advisory, while a subprocess timeout can terminate the child.

## ③ Record, then report

Adapters bind inside the process that runs the agent. They observe tool calls without requiring changes to the agent's implementation and write the trajectory to:

```text
$PERCEPTEYE_TRAJECTORY_DIR/tool_calls.jsonl
```

Each tool call receives one of three outcomes:

| outcome | meaning |
| --- | --- |
| `ok` | The tool call completed successfully. |
| `failed` | The tool call returned an execution failure. |
| `unknown` | The adapter could not determine the final outcome. |

Artifacts are collected on every path, including agent errors, deadline expiry, and other terminal failures. Collection follows these caps:

| cap | limit |
| --- | ---: |
| Single artifact | 256 MB |
| Inline content per file | 64 KB |
| Inline content per report | 256 KB |

Symlinks are never collected. The collector follows regular files within the permitted artifact paths and excludes symlink targets.

The substrate check determines whether the execution environment itself was unavailable rather than whether the agent made a poor decision.

| condition | substrate result |
| --- | --- |
| Every recorded tool call failed and at least one tool call exists | `substrate_unavailable` |
| At least one tool call succeeded | Not classified as substrate unavailable |
| No tool calls were recorded | Not classified by this check alone |

The following exclusions are emitted when a rollout cannot produce a normal scored result:

| exclusion | meaning |
| --- | --- |
| `entrypoint_error` | The configured entrypoint could not be resolved or started. |
| `agent_exit_nonzero` | The agent process exited with a non-zero status. |
| `deadline_exceeded` | The rollout exceeded its work deadline. |
| `credential_expired` | The single-use rollout credential expired. |
| `substrate_unavailable` | The execution substrate failed according to the substrate check. |
| `flywheel_crash` | The flywheel process crashed while handling the rollout. |
| `cancelled` | Declared by the contract but not currently emitted. |
| `capacity` | Declared by the contract but not currently emitted. |

After recording, the SDK reports the result with `POST /rollouts/{id}/result`. The endpoint returns an acknowledgment. Artifact collection and reporting happen regardless of whether the agent completed normally.

## ④ Score: the part you do not build

Scoring runs on the control plane. The system generates tasks from the tools your agent actually exposes, then grades trajectories against compiled checks.

You do not need to create a second test-only tool list or write a separate evaluation harness for the agent's recorded tool surface. The onboarding description supplies the surface used to generate tasks, while the adapters supply the execution evidence used to grade them.

Sign in to inspect generated tasks, scores, and promotions. A rollout result acknowledgment confirms delivery of the report, not promotion of a new policy.

## ⑤ Improve: the better agent runs the next lap

The flywheel closes when your production process reads the policy selected by the control plane.

Use these calls for policy access:

| call | purpose |
| --- | --- |
| `apply_current_policy()` | Applies the current promoted policy to the production agent. |
| `policy_source()` | Returns the policy source used to support rollback before promoting a new policy. |
| `current_prompt()` | Returns the current system prompt for an agent that uses prompt-based policy. |

`serve()` reads `GET /policy/current` at startup and prints the response without applying it. Production code must call `apply_current_policy()` when it is ready to use the promoted policy.

Use rollback first, then promotion. `policy_source()` gives you the source needed to restore the previous behavior before applying a new policy. `current_prompt()` lets prompt-driven agents read the active system prompt during their startup path.

Policy refresh does not run in a background polling thread. Refresh happens inside your call, either at startup or when your application invokes the refresh path according to its own TTL or deployment lifecycle.

The resulting loop is:

```text
describe once
  -> claim a rollout
  -> run the unchanged agent
  -> record and report evidence
  -> score against compiled checks
  -> promote a policy
  -> apply the policy at production startup
  -> claim the next rollout
```

## The five lanes

All five lanes are opened from your side. Agent Flywheel does not open a connection into your application.

| lane | routes | opened |
| --- | --- | --- |
| ⓪ Register | `GET /health`, `POST /agents`, `POST /agents/{agent_id}/rulebook` | Once at startup |
| ① Claim | `POST /rollouts/claim` | Continuously in the serving loop |
| ② Return | Heartbeat, `/result`, and `/abandon` | Once per rollout |
| ③ Policy back | `GET /policy/current` and `GET /prompt/current` | At startup or after a TTL |
| ④ Live evidence | `POST /agents`, `GET /policy/current`, `POST /rulebook`, local capture, and `POST /turns` with consent | Every 32 turns and at exit |

<Callout kind="info">

This package opens no listening socket. It uses no inbound ports, public DNS, or TLS listener. A source scan for `.listen(`, `HTTPServer`, `uvicorn`, `fastapi`, and `flask` finds no server entrypoint.

</Callout>

<Callout kind="warning">

Lane ④ does not ship yet. The `attach()` path is designed to use the same adapters and tri-state recording for live turns, but live-turn upload remains disabled unless an operator explicitly consents.

</Callout>

When available, lane ④ will bind the same adapters used for rollout recording, scope evidence to a live turn, and write the same `ok`, `failed`, or `unknown` outcomes. Upload uses `/turns` and is off by default. `trajectory_root` is required and has no default. The live-evidence path fails open, so a capture or upload failure does not block the live agent.
