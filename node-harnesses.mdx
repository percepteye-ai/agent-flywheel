## Node harnesses

One npm package supports two harnesses with zero dependencies. `@percepteye/agent-flywheel` registers as `agent-flywheel` in the host harness and records `ok`, `failed`, or `unknown` outcomes in the same trajectory format written by the Python SDK.

Install the package for the harness you use:

```bash
openclaw plugins install @percepteye/agent-flywheel
```

```bash
dsh plugin --profile <name> add @percepteye/agent-flywheel
```

The package uses Node's built-in `node:fs` and `node:path` modules only. It requires Node `>=22.22.3`.

### Harness entry points

| harness | entry module | hook | can it change the run? |
| --- | --- | --- | --- |
| OpenClaw | `src/index.js`, default export plus `register` | `api.on("after_tool_call", ...)` | No. The hook returns `void`. |
| DeepSeek Harness | `src/dsh.js`, `apply` with no default export | `ctx.on("tools/result", ...)` | No. The event is declared `@mode emit` and runs over a deep-frozen object. |

Neither mode registers a mutation seam. The plugins observe tool activity and write trajectory records, but they cannot replace the result that the agent receives.

## The mode decides which hooks are subscribed

Set `PERCEPTEYE_AGENT_MODE` to select the OpenClaw subscription set. The available modes are `training` and `production`, and `training` is the default. A `config.mode` value overrides the environment variable. An unrecognized value degrades to `production`.

| mode | OpenClaw hooks | purpose |
| --- | --- | --- |
| `both` | `after_tool_call`, `llm_input` | Record one tool outcome and describe the agent. |
| `production` | `message_received`, `agent_end`, `gateway_stop` | Capture the served turn and upload on cadence. |
| `training`, only after the plugin can claim the rollout | `session_start`, `agent_end`, `session_end`, `gateway_start`, `cron_changed`, `gateway_stop` | Claim the rollout, deliver the task, and report the result. |

The OpenClaw `both` row describes the hooks that are always paired with the selected operational mode. The operational hooks are then selected according to whether the plugin is running in production or training.

The DeepSeek Harness entry does not vary its subscription by mode. It subscribes to `tools/result` only.

## What switches it off, and where it writes

Set `PERCEPTEYE_CAPTURE=0` to disable recording. The plugin reads `PERCEPTEYE_CAPTURE` as the kill switch, so an installed plugin records nothing when the value is `0`.

For training rollouts, `PERCEPTEYE_TRAJECTORY_DIR` names the directory where the plugin appends trajectory data. The plugin reads this variable for each call rather than caching it.

Production captures use a separate turn directory under `PERCEPTEYE_CAPTURE_DIR`. The default is `~/.percepteye/captured`. Each served turn is routed to its own directory.

<Callout kind="warning">

A production install is not inert. If `PERCEPTEYE_TRAJECTORY_DIR` is unset, the plugin still captures every served turn to disk through the production capture path. Set `PERCEPTEYE_CAPTURE=0` when you want an installed plugin to record nothing.

</Callout>

<Callout kind="info">

`fw.serve()` sets `PERCEPTEYE_TRAJECTORY_DIR` for the served run. The Node plugin then writes its records to that directory.

</Callout>

The plugin writes capture data locally. It does not write output to the agent's tool result or model-facing response.

## Observe only, structurally

Both plugins are observers. They cannot alter, block, delay, or replace a tool result.

### OpenClaw hook selection

OpenClaw exposes several event surfaces, but only one provides the complete tool-call context without creating a mutation seam or requiring cross-event state.

| surface | can alter? | why it is or is not used |
| --- | --- | --- |
| `registerAgentToolResultMiddleware` | Yes. A returned value replaces what the model reads. | Not used. The recorder must not sit on a mutation seam. |
| `registerAgentEventSubscription` | No. | Not used because arguments arrive on a separate `phase:start` event and execution results are capped. Correlating both phases would require a pending map. |
| `api.on("after_tool_call", ...)` | No. The hook returns `void`. | Used. `params`, `result`, `error`, `durationMs`, and `toolCallId` arrive in one event. The recorder handles the event on a best-effort basis inside `try/catch`. |

The DeepSeek Harness `tools/result` event is declared `@mode emit`. Its execution and result objects are deep-frozen before the registry publishes them. The plugin therefore has no object mutation path, and its typed return value is `undefined`.

<Expandable title="Why two entry modules rather than one">

Cordis normalizes a plugin with `exports.default ?? exports`. OpenClaw needs a default export and a `register` function, so its entry module is `src/index.js`.

DeepSeek Harness expects the `apply` export. A default export from `src/dsh.js` would be handed to the harness instead of `apply`, so the DeepSeek Harness module must not define a default export.

</Expandable>

## What it writes

The plugin appends one JSON object for each tool call to:

```text
$PERCEPTEYE_TRAJECTORY_DIR/tool_calls.jsonl
```

Each line is an independent JSON object. The following records show representative outcomes from both harnesses:

```json
{"name":"exec","arguments":{"command":"exit 3"},"outcome":"failed","status_code":null,"error":"(Command exited with code 3)","error_class":"ToolError","latency_ms":91,"agent_name":"main","tool_call_id":"call_percepteye_1"}
```

```json
{"name":"mcp__jira__create_issue","arguments":{"project":"ENG"},"outcome":"unknown","status_code":null,"latency_ms":412,"agent_name":"main","tool_call_id":"call_2","entity_ids":{"id":"10001","key":"ENG-7"}}
```

```json
{"name":"bash","arguments":{"command":"npm run dev &"},"outcome":"unknown","status_code":null,"error_class":"StillRunning","agent_name":"main","tool_call_id":"tc_9"}
```

### Record fields

| field | presence | description |
| --- | --- | --- |
| `name` | Always | Name of the tool that ran. |
| `arguments` | Always | The actual arguments passed to the tool. |
| `outcome` | Always | One of `ok`, `failed`, or `unknown`. |
| `status_code` | Always | Always `null` in Node records. |
| `error` | When the host states an error | Host-provided error text. Values longer than 4,000 characters are elided with a marker. |
| `error_class` | When classified | One of `ToolError`, `ExitStatus:<n>`, `ExitStatusUnreadable`, `StillRunning`, `Aborted`, `TimedOut`, `Signal:<name>`, or a DeepSeek Harness information code. |
| `latency_ms` | OpenClaw only | Tool-call latency in milliseconds. |
| `agent_name` | When the host names an agent | Name supplied by the host. |
| `tool_call_id` | When present | Host-provided identifier for the tool call. |
| `entity_ids` | When non-empty | Shallow identity values extracted from the tool result. |

Neither plugin writes output to the tool result. Entity extraction considers only `id`, `key`, `uuid`, `sid`, and `gid`. It searches up to depth 3 and a maximum of 2,000 nodes. The shallowest matching values win, and ambiguous values are dropped. Fields such as `name`, `number`, `title`, `label`, `summary`, and `description` never identify an entity.

`entity_ids` is emitted for every outcome when an entity is found, including `unknown` outcomes.

The file is append-only and opened with `O_APPEND`. The plugin flushes each call before continuing. A write failure never reaches your agent.

## How the outcome is decided

The recorder preserves uncertainty. It never rounds `unknown` up to `ok`.

OpenClaw reports `details.status: "completed"` when a command process finishes, including a command that exits with status 3. `completed` means that the process finished, not that the command succeeded. The plugin reads the exit code when it can.

### OpenClaw outcome rules

| condition | outcome | error class or behavior |
| --- | --- | --- |
| The host sets a non-empty error | `failed` | `ToolError` |
| `exec` or `bash` exits with code 0 | `ok` | None |
| `exec` or `bash` exits with a non-zero code | `failed` | `ExitStatus:<n>` |
| `exec` or `bash` exits but the status cannot be read | `unknown` | `ExitStatusUnreadable` |
| `read`, `write`, `edit`, `grep`, `ls`, or `find` completes without an error | `ok` | None |
| Any other tool, including MCP and third-party tools | `unknown` | Host-specific information may be retained |

`apply_patch` is deliberately not included in the silent-success set. The plugin does not infer success for it from the absence of an error.

### DeepSeek Harness outcome rules

| condition | outcome | error class or behavior |
| --- | --- | --- |
| `isError: true` | `failed` | Carries the DeepSeek Harness error class. |
| `isError` is absent | `unknown` | Absence is not treated as `false`. |
| Foreground `bash` or `pwsh` exits with code 0 | `ok` | None |
| Foreground `bash` or `pwsh` exits with a non-zero code | `failed` | `ExitStatus:<n>` |
| `timedOut: true` | `failed` | `TimedOut` |
| The process is killed by a signal | `failed` | `Signal:<name>` |
| `kind: "background"` | `unknown` | `StillRunning`, because launch does not mean completion |
| `aborted: true` | `unknown` | `Aborted`, because cancellation is not an agent mistake |
| The exit status cannot be read | `unknown` | `ExitStatusUnreadable` |
| `read`, `write`, `edit`, `read_image`, `str_replace_editor`, or `todo_write` has `isError: false` | `ok` | None |
| Any other tool state | `unknown` | Host-specific information may be retained |

`isError: false` does not mean success for every DeepSeek Harness tool. It is a silent-success signal only for the explicitly listed tools.

The DeepSeek Harness `bash` tool renders a failing exit as text appended to the model-facing content. The recorder still classifies the non-zero exit as `failed` with `ExitStatus:<n>`.

For background processes, cancellation, timeouts, and unreadable exit statuses, the recorder preserves the distinction between a known failure and a result that cannot establish success.

## Describing the agent in OpenClaw

OpenClaw's `llm_input` hook discovers the agent description and writes it to:

```text
$PERCEPTEYE_TRAJECTORY_DIR/discovered_agent.json
```

The hook records the framework as `openclaw`, uses `openclaw_llm_input` as the source type, and selects the richest available tool catalogue. It writes the file with a write-then-rename sequence.

| field or condition | behavior |
| --- | --- |
| `framework` | Always `openclaw` for this hook. |
| `source_type` | `openclaw_llm_input`. |
| Tool catalogue | The richest discovered catalogue wins. |
| `tool_definitions` | Preserves the distinction between `null` and `[]`. |
| NUL bytes | Stripped before the description is written. |
| Plugin not opted into conversation access | The recorder still works, but the agent remains unreadable. |

<Callout kind="warning">

`llm_input` is a conversation hook. OpenClaw refuses to register it for a non-bundled plugin unless the operator opts in with `hooks.allowConversationAccess=true`. Without that opt-in, the plugin loads and records tool outcomes, but it cannot describe the agent and the agent remains unreadable.

</Callout>

## What it cannot see: describe

Observation cannot recover information that the harness never exposes. Use the declaration configuration when you need to describe the agent's system prompt, tools, or read-only state.

The Node declaration is a rule-for-rule port of the Python SDK's `describe=` configuration. A configuration can declare the system prompt, tool definitions, and whether the agent is read-only:

```json
{
  "describe": {
    "system_prompt": "You manage engineering issues and report each completed action.",
    "tools": [
      "mcp__jira__create_issue",
      "mcp__jira__update_issue"
    ],
    "read_only": false
  }
}
```

The declaration uses the same rules, the same wire record, and the same refusal behavior as the Python SDK. What you declare takes precedence over what observation discovers. Anchors do not establish execution identity.

Three differences are forced by the host:

1. An invalid declaration warns instead of throwing.
2. `introspect: false` with `describe` warns instead of refusing the declaration.
3. Observed data uses `framework: "openclaw"` rather than `framework: "custom"`.

Declaration and observation follow the same consent and refusal semantics as the Python SDK. A declaration does not grant access to information that the host has refused to expose.

## A product's workflow rules: rules

The `rules=` configuration describes product workflow rules separately from the agent declaration. It uses the same request and produces the same receipt as the Python SDK.

An empty list retracts previously sent rules. An unset value sends nothing:

```json
{
  "rules": []
}
```

Use the rules configuration when the product needs to replace its current workflow rules with an empty set. Do not treat an unset configuration as a retraction.

Rule submission is never fatal. Invalid or unavailable rule data does not stop the agent run.

## The two halves cannot drift

The Node and Python SDKs share a cross-language ABI. The ABI check compares the records and decisions produced by the two implementations so that a harness integration does not silently diverge from the Python SDK.

The check runs as two commands from the two SDK repositories. The script resolves the Node SDK from `PERCEPTEYE_NODE_SDK` when that variable is set. If the variable is unset, it also checks for a sibling checkout. If neither location exists, the check skips instead of failing.

Run the check from the repository's ABI-check workflow after making changes to classification, trajectory fields, declaration handling, or workflow rules. Keep the Node and Python fixtures aligned when you add a new host condition.

CI runs the cross-language check on Node 22 and Node 24. This catches differences in serialization, outcome classification, entity extraction, and wire-compatible trajectory records before either implementation is released.
