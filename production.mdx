## Run a production agent separately from training

Your production agent is a different process from the one doing training work. `serve()` claims rollouts and runs them in child processes, while the production agent picks up the model and prompt produced by training and can optionally contribute evidence from live turns.

None of these operations requires a redeploy. None opens an inbound port.

<Callout kind="warning">

For your production agent, never for `serve()`: use `apply_current_policy()`, `policy_source()`, and `current_prompt()` in the agent serving users. `serve()` is for claiming rollouts and running training work in child processes.

</Callout>

The production workflow has four independent concerns:

- Pick up the current model endpoint and credentials at startup.
- Refresh policy changes while the process continues serving traffic.
- Validate and apply the currently served prompt.
- Capture evidence from turns without rerouting or changing execution.

The sections below describe each concern and the storage behavior around captured trajectories.

## One shot, at startup

Use `apply_current_policy()` when the production process starts. The function performs one `GET /policy/current`, resolves the credentials, and returns the configuration needed by the model client.

```python
policy = apply_current_policy(agent_id="support-agent")

if policy:
    print(f"Serving {policy['model']} from {policy['base_url']}")
```

A successful response contains the current endpoint configuration:

| Key | Meaning |
| --- | --- |
| `base_url` | Base URL for the model endpoint. |
| `api_key` | API key resolved for the endpoint. |
| `model` | Model identifier selected by the current policy. |

The function returns an empty dictionary, written as `{}`, when the current configuration should remain unchanged. It never raises an exception into startup. Your process can therefore continue with its existing configuration when the control plane is unavailable or has no new configuration to apply.

### Credential resolution

`apply_current_policy()` resolves the API key in this order:

| Order | Source | When it applies |
| --- | --- | --- |
| 1 | The `api_key` argument | You pass an API key directly to the function. |
| 2 | The environment variable named by `endpoint.api_key_env` | The current policy specifies an environment variable for the endpoint credential. |
| 3 | `PERCEPTEYE_API_KEY` | The policy does not provide a more specific credential source. |

The function does not export environment variables by default. Pass `set_env=True` when the model client reads `OPENAI_BASE_URL` and `OPENAI_API_KEY` from the environment:

```python
policy = apply_current_policy(
    agent_id="support-agent",
    set_env=True,
)
```

With `set_env=True`, the function exports:

- `OPENAI_BASE_URL`
- `OPENAI_API_KEY`

Use this option only when the client in the production process is configured to read those variables. Otherwise, use the returned dictionary and configure the client explicitly.

### Lower-level policy functions

Use the lower-level functions when you need to inspect the raw policy body or construct endpoint arguments yourself.

| Function | Behavior |
| --- | --- |
| `current_policy()` | Returns the raw body from `GET /policy/current`. |
| `endpoint_kwargs()` | Parses the policy body into endpoint keyword arguments. |
| `apply_current_policy(agent_id=...)` | Resolves and applies the production endpoint configuration at startup. |

`current_policy()` is useful when you need fields that `endpoint_kwargs()` does not expose. `endpoint_kwargs()` is useful when your client setup already accepts keyword arguments and you want to keep policy retrieval separate from client initialization.

## A handle that keeps up

Use `policy_source()` when the production process must notice policy changes without restarting. The handle caches the current policy and refreshes it when you call `current()`.

```python
source = policy_source(agent_id="support-agent", ttl_s=300)

while serving_requests():
    snapshot = source.current()

    if snapshot.changed:
        reload_model_endpoint(
            base_url=snapshot.base_url,
            api_key=snapshot.api_key,
            model=snapshot.model,
        )

    handle_request()
```

Call `current()` once per turn or request boundary where a policy change should become visible. `policy_source()` does not refresh in the background, so a process that never calls `current()` does not observe a new policy.

`ttl_s` is the caller's preferred refresh interval. The server can provide a refresh hint that takes precedence over your value, subject to the minimum interval and jitter described below.

### PolicySnapshot fields

Each call to `current()` returns a `PolicySnapshot`:

| Field | Type | Meaning |
| --- | --- | --- |
| `base_url` | `str` | Model endpoint base URL in the current snapshot. |
| `api_key` | `str` | API key in the current snapshot. |
| `model` | `str` | Model identifier in the current snapshot. |
| `changed` | `bool` | `True` once when the observed policy has changed for this handle. |
| `stale_for_s` | `float` | Number of seconds the snapshot has been stale. It is `0.0` while refreshes succeed. |
| `last_refresh_ok` | `bool` | Whether the most recent refresh succeeded. |
| `serving_generation` | `str` | Generation identifier associated with the policy being served. |

Use `stale_for_s` to decide when to alert. Do not use `serving_generation` to determine whether the snapshot changed. `changed` is the explicit change signal and is consumed as an edge: it is true for one snapshot and then returns to false until another policy transition occurs.

A snapshot is truthy when it contains something for the production agent to act on:

```python
snapshot = source.current()

if snapshot:
    emit_policy_metrics(
        model=snapshot.model,
        stale_for_s=snapshot.stale_for_s,
        refresh_ok=snapshot.last_refresh_ok,
    )
```

### Handle policy changes with on_change

Register `on_change` when you want a callback for policy transitions:

```python
def reload_policy(snapshot):
    reload_model_endpoint(
        base_url=snapshot.base_url,
        api_key=snapshot.api_key,
        model=snapshot.model,
    )

source = policy_source(
    agent_id="support-agent",
    ttl_s=300,
    on_change=reload_policy,
)
```

The callback fires for:

| Event | Callback fires |
| --- | --- |
| A policy is promoted | Yes |
| A policy is rolled back | Yes |
| A refresh fails | No |
| A refresh succeeds but nothing is deployed | No |

Exceptions raised by `on_change` are swallowed. Keep the callback focused on updating the serving process and emit failures through your own metrics or logs if you need operational visibility.

### Nothing polls in the background

`policy_source()` does not create a thread, timer, or task. Refresh work happens inside the call to `current()`.

| Refresh behavior | Value |
| --- | --- |
| Default TTL | `300` seconds |
| Server refresh hint | Takes precedence over the caller's `ttl_s` value |
| Minimum TTL | `30` seconds |
| Jitter | Plus or minus `10%` |
| Jitter timing | Chosen once when the handle is constructed |
| Refresh budget | `1` second |
| Attempts per refresh | One |

The jitter is stable for the lifetime of a handle. Constructing a new handle chooses a new jitter value, but repeated calls to `current()` on the same handle do not continually move its refresh deadline.

### Serve stale, always

A failed refresh is a non-event. The current snapshot remains available, and the handle serves that snapshot instead of replacing it with an error state.

Concurrent callers do not create a refresh stampede. One caller performs the refresh, and the remaining callers receive the cached snapshot.

Use `PolicySource` as a context manager when you want its lifecycle to be explicit:

```python
with policy_source(agent_id="support-agent") as source:
    while serving_requests():
        snapshot = source.current()
        serve_with(snapshot)
```

<Expandable title="What policy_source() will not do">

| It will not | What that means |
| --- | --- |
| Choose an arm | The handle observes the policy selected by the control plane. It does not select between candidates. |
| Damp flapping | The handle does not add promotion or rollback stabilization. |
| Set environment variables | `policy_source()` does not provide the `set_env` behavior of `apply_current_policy()`. |
| Work with `serve()` | Use the handle in the production agent, not in the process claiming training rollouts. |

</Expandable>

## The prompt

Use `current_prompt()` to retrieve the prompt currently served for an agent. Prompt retrieval uses a separate `GET /prompt/current` endpoint from policy retrieval.

Use `prompt_decision(served)` to determine whether the returned prompt is safe to apply. Do not re-derive the decision by inspecting individual fields yourself.

```python
served = current_prompt(agent_id="support-agent")
decision = prompt_decision(served)

if decision.apply:
    install_system_prompt(decision.text)
else:
    record_prompt_refusal(
        reason=decision.reason,
        status=served.get("candidate_status"),
    )
```

The served prompt can contain the following fields:

| Field | Meaning |
| --- | --- |
| `name` | Prompt name. |
| `version` | Prompt version. |
| `text` | Prompt text currently served by the control plane. |
| `sha256` | SHA-256 checksum for the served prompt text. |
| `candidate_kind` | Kind of candidate represented by the prompt. |
| `status` | Candidate delivery or approval status. |
| `model_prompt_checksum` | Checksum recorded for the prompt associated with the model. |
| `stale_baseline` | Whether the prompt is based on stale information. |

### Prompt refusal rules

`prompt_decision()` refuses to apply a prompt for any of these reasons:

| Refusal reason | Condition |
| --- | --- |
| No text | The served prompt has no usable text. |
| Stale baseline | `stale_baseline` is true. |
| Unapproved status | The status is not `approved` or `delivered`. |
| Checksum mismatch | Both `sha256` and `model_prompt_checksum` are present, and they differ. |

`decision.apply` is true only when all acceptance conditions hold. When the decision refuses the prompt, `decision.text` is `None`.

An empty dictionary, written as `{}`, means keep the prompt already installed in the production process. `current_prompt()` does not apply the text for you. This differs from `apply_current_policy()`, which is designed to resolve and apply the startup endpoint configuration.

## Attach evidence from live turns

`serve()` handles training work. `attach()` records what an agent is already doing while it serves users in production.

The attachment captures evidence but never reroutes execution. It binds with an empty LLM URL and API key, so attaching an agent does not replace the model endpoint used by your application.

```python
px = attach(
    agent_id="support-agent",
    trajectory_root="/var/lib/agent-flywheel/trajectories",
    execution_entrypoint="support_agent.run",
    execution_input_shape="text",
    execution_method="run",
    describe="Customer support production agent",
)

try:
    with px.turn(input_text="How do I change my billing email?") as turn:
        answer = support_agent.run(turn.input_text)
        turn.record_answer(answer)
finally:
    px.close()
```

The `trajectory_root` is required because retaining production trajectories is a deliberate operational decision. Choose a durable location with enough capacity for the retention policy you intend to operate.

### attach() parameters

| Parameter | Meaning |
| --- | --- |
| `agent_id` | Required identifier for the production agent. |
| `trajectory_root` | Required local root for append-only trajectory data. |
| `adapters` | Adapter selection. Defaults to `auto`. |
| `register` | Whether to register the agent with the control plane. Defaults to `True`. |
| `control_plane_url` | Control plane URL. If omitted, the value is resolved from the environment. |
| `api_key` | Control plane API key. If omitted, the value is resolved from the environment. |
| `execution_entrypoint` | Optional entry point used to identify the executed agent. |
| `execution_input_shape` | Shape of the execution input. Defaults to `text`. |
| `execution_method` | Optional method used to invoke the execution entry point. |
| `attested_execution_components` | Optional attested execution components used for execution identity. |
| `describe` | Human-readable description of the production agent. |
| `rules` | Optional rule configuration for the attachment. |

When `register=True`, registration performs `POST /agents` and then `GET /policy/current`. The registered mode is `production`.

If you omit `execution_entrypoint`, registration sets `discovered_agent` to `null`. Attachment and upload operations fail open, so an attachment problem does not fail the production turn.

### Attachment object

`attach()` returns an attachment object with the following interface:

| Member | Purpose |
| --- | --- |
| `.turn()` | Opens a declared turn boundary as a context manager. |
| `.record_answer()` | Records the answer associated with the current turn. |
| `.read()` | Reads attachment or trajectory data. |
| `.read_turn()` | Reads a specific turn. |
| `.flush()` | Uploads pending records subject to the flush cap. |
| `.policy` | Informational policy state associated with the attachment. |
| `.agent_fingerprint` | Fingerprint for the attached agent identity. |
| `.adapters_bound` | Adapters bound to the attachment. |
| `.rulebook` | Rulebook available to the attachment. |
| `.rulebook_refusal` | Reason a rulebook was refused, when applicable. |
| `.wait_for_rulebook()` | Waits for the rulebook result. |
| `.close()` | Closes the attachment and releases its local resources. |

### Declare the turn boundary

The turn boundary is declared by your code. `attach()` does not infer where a turn starts or ends from arbitrary application activity.

```python
with px.turn(
    input_text="Summarize the incident report",
    task_id="incident-2025-04-18-0042",
) as turn:
    answer = run_agent(turn.input_text)
    turn.record_answer(answer)
```

`task_id` is correlation evidence, not authority. The attachment uses the explicit `turn()` boundary to decide what belongs to a turn.

Nothing inside `turn()` can fail the production turn. Capture errors do not interrupt the application operation.

### Consent and captured content

Turn text capture is opt-in. Provide `input_text` and call `record_answer()` when you want the input and answer included in the captured turn.

Model content capture is a separate consent tier and is off by default. Inspect the attachment state when you need to understand why model content was not captured:

| Member | Meaning |
| --- | --- |
| `may_capture_model_content` | Whether the second consent tier permits model content capture. |
| `model_content_refusal` | Reason model content capture was not permitted. |

Record tool calls inside the active turn:

```python
with px.turn(input_text="Find the latest invoice") as turn:
    invoice = billing_lookup(customer_id="cus_7f3a91d2")
    turn.record_tool_call(
        name="billing_lookup",
        arguments={"customer_id": "cus_7f3a91d2"},
        result=invoice,
    )
    turn.record_answer(format_invoice(invoice))
```

Execution identity is optional for attachment, but when configured it is fail-closed. An execution identity that cannot be attested is not accepted as an identified execution.

`PERCEPTEYE_AGENT_MODE` does not gate `attach()`. Setting or omitting that environment variable does not determine whether attachment is enabled.

### What the attachment ships and when

The attachment sends captured turns with `POST /turns`.

| Behavior | Details |
| --- | --- |
| Capture consent | Per-agent capture consent is off by default. |
| Upload permission | Inspect `may_upload` before relying on upload behavior. |
| Upload refusal | Inspect `upload_refusal` when uploading is not permitted. |
| Enabling capture | Enabling capture does not require a process restart. |
| Background cadence | Pending records upload every 32 turns on a daemon thread. |
| Process shutdown | An `atexit` hook attempts to flush pending records. |
| Explicit flush | `flush(batch_size)` sends at most 64 records in one call. |

The daemon thread handles periodic upload after capture is enabled. Your application can call `flush()` at an operational boundary when it needs to send pending records sooner, but the call remains subject to the maximum batch size of 64.

## Identify the active capture

Use `current_capture()` when code needs to know which capture context is active:

```python
capture = current_capture()

match capture:
    case ("rollout", rollout_id):
        record_context(kind="rollout", capture_id=rollout_id)
    case ("turn", turn_id):
        record_context(kind="production_turn", capture_id=turn_id)
    case None:
        record_context(kind="none")
```

`current_capture()` returns one of three states:

| Return value | Meaning |
| --- | --- |
| `("rollout", rid)` | Code is running inside a training rollout. |
| `("turn", tid)` | Code is running inside an attached production turn. |
| `None` | No rollout or attached turn is active. |

<Callout kind="warning">

`current_rollout_id()` is not a rollout-versus-production test. Inside `attach().turn()`, it returns the turn's ID, so use `current_capture()` when you need to distinguish rollout execution from production turn capture.

</Callout>

## Retain trajectory data

Production trajectories are append-only and grow without bound unless you configure pruning. At approximately one million turns, storage can reach about 2.4 GB and one million inodes.

Set `retention_turns` when you want periodic pruning:

```python
px = attach(
    agent_id="support-agent",
    trajectory_root="/var/lib/agent-flywheel/trajectories",
    retention_turns=100000,
)
```

The retention scan runs once every 256 turns. The scan does not delete records more frequently than that interval.

You can also prune explicitly:

```python
prune(keep_last=100000)
prune(older_than_s=30 * 24 * 60 * 60)
```

Use `keep_last` to retain a fixed number of recent turns. Use `older_than_s` to remove turns older than a time threshold.

<Callout kind="info">

Nothing is deleted unless you ask. Trajectory data remains on disk until you configure `retention_turns` or call `prune()` explicitly.

</Callout>

Choose a retention policy before selecting `trajectory_root`. The root determines where the append-only data grows, while the retention setting determines when your process scans and removes older records.

## Understand durability

Captured records are flushed but never fsynced. A flush writes pending data so it survives the process dying, but it does not provide the power-loss guarantees of an fsync.

| Event | Expected outcome |
| --- | --- |
| Process exits or dies after a flush | Flushed records survive. |
| Machine loses power | Recent outcomes can be lost because records were not fsynced. |
| Explicit fsync implementation | Would protect against power loss, at an estimated cost of 1 to 10 ms per record. |

Design production recovery around the possibility that a machine crash loses recent outcomes. If power-loss durability is required, account for the additional 1 to 10 ms per-record cost of fsync rather than treating a flush as equivalent.
