## Run a non-Python agent

Not Python? Pass an argv list instead of an import path. A compiled binary, a Node CLI, or anything with a command line can run as an Agent Flywheel agent. You do not need to implement a protocol or change the existing CLI.

```python
fw.serve(["opencode", "run"], agent_id="coding-agent", input_shape="text")
fw.serve(
    ["dsh", "--profile", "headless", fw.TASK],
    agent_id="dsh-agent",
    input_shape="text",
)
```

A list or tuple as the first argument tells Agent Flywheel that the agent is a process, not a Python object. Agent Flywheel does not import or resolve the value. Process isolation is inherent, and options such as `method=` and Python object adapters do not apply to this path.

## The task, three channels

Agent Flywheel delivers each task through three channels. The first two channels are always present. The argv channel is used only when `fw.TASK` appears in the argv list.

| Channel | When it is used | Details |
| --- | --- | --- |
| `stdin` | Always, unless `fw.TASK` appears in argv | The task is written to stdin, then stdin is closed. |
| `PERCEPTEYE_TURN_INPUT` | Always | Contains the task. The variable is inert unless the CLI reads it. |
| An argv position | Only where `fw.TASK` appears | Every occurrence of the sentinel is replaced with the task. |

The first two channels are sent together because CLIs differ, and choosing the wrong input channel can fail silently. When `fw.TASK` appears in argv, Agent Flywheel sends an empty string through stdin while leaving `PERCEPTEYE_TURN_INPUT` set.

`fw.TASK` is a sentinel object, not the string `{task}`. Agent Flywheel substitutes the task at each argv position that contains the sentinel. It passes argv directly to `Popen` and never invokes a shell.

<Callout kind="alert">

**argv is visible; stdin is not.** Anything placed in argv can be read through `ps`. Use `fw.TASK` when the CLI genuinely cannot read stdin or an environment variable, not as the default input channel.

</Callout>

## What comes back

Agent Flywheel trims stdout and uses the result as the final text. For a structured stream, the runner projects the terminal assistant message instead of treating the raw stream as the answer.

| Process result | Recorded outcome | Answer | Details |
| --- | --- | --- | --- |
| Exit code `0` | None | Yes | The trimmed stdout or projected assistant message is returned. |
| Non-zero exit code | `agent_exit_nonzero` | Yes | The answer is retained, with an exclusion containing `exit <n>` and the last 1,500 characters of stderr. |
| Killed after the deadline | `deadline_exceeded` | Yes | The answer is retained, with an exclusion. |
| Binary cannot start | None | No | Process spawning raises, and the rollout is abandoned as `flywheel_crash`. |

An excluded answer is not discarded. `agent_exit_nonzero` is separate from `entrypoint_error`, so a process that produced an answer before exiting unsuccessfully remains distinguishable from an entrypoint failure.

<Callout kind="info">

Stderr is kept only on the non-zero path. A successful process does not add stderr to the result.

</Callout>

For structured output, see [outcomes](/outcomes) for how results and exclusions are represented.

## The working directory is the rollout

Agent Flywheel starts each rollout's child process with its current working directory set to that rollout's directory. The directory is also available through `PERCEPTEYE_TRAJECTORY_DIR`.

Files left in the working directory become artifacts and are collected after the rollout. The trajectory file `tool_calls.jsonl` is not collected as an artifact because it is the execution trajectory.

| Behavior | Result |
| --- | --- |
| Child working directory | The rollout directory, also available as `PERCEPTEYE_TRAJECTORY_DIR`. |
| Files created there | Collected as rollout artifacts. |
| Symlinks | Recorded as `skipped:symlink`. |
| Default artifact root | `$PWD/.percepteye-artifacts`. |
| Recommended artifact location | Point `artifacts_dir` outside any checkout. |

The artifact directory is removed after the report is produced. Keep deliverables inside the rollout directory so Agent Flywheel can collect them before cleanup.

## The child's environment

Agent Flywheel provides rollout metadata, task input, and provider connection details through the child's environment.

| Variable | Value |
| --- | --- |
| `PERCEPTEYE_ROLLOUT_ID` | The current rollout's identifier. |
| `PERCEPTEYE_TRAJECTORY_DIR` | The rollout directory and current working directory. |
| `PERCEPTEYE_TURN_INPUT` | The task input. |
| `OPENAI_BASE_URL`, `OPENAI_API_BASE`, `ANTHROPIC_BASE_URL` | Per-rollout provider gateway URLs. |
| `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` | Single-use credentials for the rollout's provider gateway. |

The `PERCEPTEYE_` namespace is never inherited from the parent environment. Agent Flywheel also removes unroutable provider variables, including Azure, Gemini or Vertex, Bedrock bearer token, and OpenAI-compatible reseller variables.

At startup, `serve()` warns if an unroutable provider variable is still set in the parent environment.

### endpoint_env

Use `endpoint_env` when the agent reads provider configuration under variable names other than the standard OpenAI or Anthropic names.

```python
fw.serve(
    ["dsh", "--profile", "headless", fw.TASK],
    agent_id="dsh-agent",
    input_shape="text",
    endpoint_env=("DEEPSEEK_BASE_URL", "DEEPSEEK_API_KEY"),
)
```

The declared names are added to the child environment. The standard OpenAI and Anthropic names remain available as well. Agent Flywheel uses only the names you declare and never discovers endpoint variables by inspecting the child process.

### gate_flag

Use `gate_flag` when your binary spells its completion gate with a CLI flag.

```python
fw.serve(
    ["prime-agent", "--mode", "json"],
    agent_id="prime-agent",
    gate_flag="--autonomous-gate",
)
```

`gate_flag` describes the binary's interface. The task supplies the gate command through `metadata["completion_gate"]`. When both values are present, Agent Flywheel appends the gate command to the end of argv.

## Timeouts kill the process group

`rollout_timeout_s` defaults to `900.0` seconds. Agent Flywheel caps the effective timeout at the available budget minus a 10-second margin.

When a rollout reaches its deadline, Agent Flywheel sends `SIGKILL` to the process group. Killing the group rather than only the parent matters because a CLI can spawn children that continue holding the stdout pipe open. On POSIX systems, Agent Flywheel starts the child with `start_new_session=True` so the process group can be terminated together.

Windows does not provide process groups through the same mechanism. The process-group behavior described above applies to POSIX systems.

## Tool outcomes with no instrumentation

You can recover tool-call outcomes without adding Agent Flywheel code inside the agent. Use one of two routes:

1. Parse the event stream the CLI already prints with `command_output_adapter`.
2. Append tool-call records to the rollout trajectory from the shell.

Both routes produce tool-call data outside the agent's application code.

### Route 1: An explicit adapter for the event stream your CLI already prints

Set `command_output_adapter` to an adapter that understands the CLI's stdout format. The adapter joins start and end events by call ID, extracts tool metadata, and records a tri-state outcome.

| Adapter or helper | Start event | End event | Extracted fields |
| --- | --- | --- | --- |
| Prime example adapter | `tool_execution_start` | `tool_execution_end` | `toolCallId`, `toolName`, `args`, `result`, `isError` |
| Generic `OTEL_GENAI` helper | `gen_ai.tool.start` | `gen_ai.tool.end` | `gen_ai.tool.call.id`, `gen_ai.tool.name`, `gen_ai.tool.input`, `gen_ai.tool.output`, `error.type` |

The verdict is deliberately tri-state. An unknown outcome is not rounded up to success.

| Error value | Verdict |
| --- | --- |
| `true` | `failed` |
| A non-empty string | `failed` |
| `false` | `ok` |
| An empty or whitespace-only string | `unknown` |
| No error flag | `unknown` |

The parser applies these extraction rules:

- Join start and end events by call ID.
- Drop events with no resolvable tool name.
- Skip lines that cannot be parsed.
- Set `tool_calls` to `null` when the stream contains no tool events.
- Read latency from `result.details.durationMs` when present.
- Read entity IDs from the structured result.
- Set `status_code` to `null`.
- Read only stdout.
- Preserve configured adapter capture across every exit path.

The adapter does not need to read stderr. Stderr remains part of the non-zero process result described in [What comes back](#what-comes-back).

### Route 2: Append to the trajectory from a shell

A CLI can write tool-call records directly to the trajectory file without importing Agent Flywheel code.

```bash
printf '%s\n' \
  '{"name":"read_file","outcome":"ok","details":{"path":"src/server.ts"}}' \
  >> "$PERCEPTEYE_TRAJECTORY_DIR/tool_calls.jsonl"
```

Write one JSON object per line. Each object must include `name` and `outcome`. The allowed outcomes are `ok`, `failed`, and `unknown`.

One unreadable line affects only that line. Agent Flywheel records the number of omitted lines as `tool_calls_omitted_count`.

Trajectory data takes precedence over tool events parsed from stdout. If both sources provide tool calls, the trajectory is authoritative.

## Registration: describing a CLI agent

A CLI agent has no Python object for Agent Flywheel to reflect on. Instead, `serve()` performs a warm-up at registration time in the `_describe` directory.

The warm-up sends the request `Reply with the single word: ready`, then terminates the process. It is not a rollout. Agent Flywheel allows a 60-second settle window and a 90-second warm-up timeout. A loopback observer with a dummy key handles the warm-up.

The registration path depends on the available integration:

| Agent type | Description source |
| --- | --- |
| Node agent with a plugin | The host writes `discovered_agent.json`. |
| CLI without a plugin | Agent Flywheel describes it from the completion request. |
| CLI with `introspect=False` | Warm-up introspection is skipped. |
| CLI with `describe=` | The supplied description is used without spawning the binary. |

Use `introspect=False` when starting the binary during registration is undesirable. Use `describe=` when you already know the agent's metadata and want to declare it directly.

## Worked example: prime-agent

The `prime-agent` example is a real TypeScript coding agent that does not contain Agent Flywheel code. Its CLI integration uses structured JSON output and an optional execution snapshot.

| Piece | Why it is used |
| --- | --- |
| `--mode json` and `PrimeAgentOutputAdapter()` | Projects tool events, assistant output, and call lifecycle data from stdout. |
| `PrimeHarnessSnapshot(...)` | Provides optional execution isolation and attestation. |
| `-e route.ts` | Reads `OPENAI_BASE_URL` and registers the provider. |
| `--provider percepteye --model ...` | Registers a provider without selecting it. |
| `--no-session` | Prevents continual-harness refinement from changing replicas. |
| `gate_flag="--autonomous-gate"` | Provides a completion gate. Without a gate, the limit is the only exit condition. |
| `artifacts_dir` outside the checkout | Gives the agent shell access without placing artifacts in the repository. |

### prime-agent's `isError` is not the whole truth

In JSON mode, `PrimeAgentOutputAdapter()` reads `tool_execution_start` and `tool_execution_end` events. Prime sets `isError` to `false` when a tool returns without throwing, but the actual tool result can still report an error.

The parser checks explicit failure evidence in `result.details.status` before accepting a `false` error flag. A result with `status: "error"` is therefore recorded as failed even when `isError` is `false`.

### JSON mode stdout is not the answer

Prime writes JSONL events to stdout rather than printing prose as a separate final answer. The adapter projects the final assistant text from those events.

If the process is killed before it emits a final assistant message, the answer is empty. Refinement and compaction markers can also make the trace unsuitable for training.

## What argv does not give you

Using an argv list provides process execution and isolation, but it does not provide Python-object integration features.

- No Python object adapters. Use `command_output_adapter` or append JSONL to the trajectory.
- No `method=` or `input_shape` shaping. Those options are not validated on the process path.
- No `record_tool_call()`. That is an in-process call; append JSONL instead.
- No filesystem sandbox. Isolation consists of the process boundary and environment scrubbing.
